# Product discovery, AI assessment and PayPal Sandbox — incident analysis

**Date:** 8 November 2026 · **Branch:** `perez` · **Production impact:** Users reported intermittent analysis HTTP 500 and confusing dual-button search behavior; PayPal rejected a buyer login because it matched the seller account.

## 1. Confirmed root cause of the intermittent AI 500

In `backend/app/api/procurement_requests.py` the lazy AI import block had literal two-character backslash-n (`\\n`) sequences instead of Python line breaks. The complete imports and `settings = get_settings()` were therefore included in a physical **comment**, not executed.

The failure was conditional:

- If no saved Channel3 evidence existed, the old `/analyze` path called `/discover`-equivalent logic, saved results and tried to analyze them.
- If there were **no eligible in-stock offers**, an early rule-based, zero-model assessment returned without touching the broken imports.
- If eligible offers existed and no AI assessment was cached, the model path referenced undefined `settings` / `runtime`, causing an unhandled `NameError` and HTTP 500.
- Prior successful Channel3 snapshots remained visible because their database transaction committed **before** the AI path failed. They were **not necessarily generated by fallback AI models**.

This is confirmed from the checked-in Python source. Vercel runtime logs remain permission-restricted, so the actual live exception stack has not been independently retrieved. The source error fully explains the observed conditional symptom.

## 2. Independent buttons and data provenance

| User action | Network route | Correct behavior |
| --- | --- | --- |
| **Search products** | `POST /api/v1/procurement-requests/{id}/discover` | Fetch real Channel3 products, rank against rules, persist source/time and eligibility, invalidate any previous AI answer. Does not call Gemini/Groq/OpenRouter. |
| **Ask AI to analyze** | `POST /api/v1/procurement-requests/{id}/analyze` | Requires preexisting saved Channel3 results (HTTP 409 before search). Consumes only saved and sanitized evidence; does not automatically search Channel3 again. Uses bounded ADK model calls only if there are eligible offers, subject to quota. |
| **No eligible products** | Same AI route | Returns an explicitly labelled `catalogue_only` assessment without spending tokens or inventing shopping evidence. |
| **Transient provider outage** | Same AI route | When known transient categories exhaust configured models, retains cached offers and returns a clearly identified retryable, deterministic `catalogue_only` assessment. |
| **Authentication/unsupported model errors** | Same AI route | Returns a safe 502/503 diagnostic rather than silently attributing a fallback to Gemini. Saved offers remain usable but a model assessment has not succeeded. |

The frontend now disables AI until a real Channel3 search exists, uses independent per-action pending text, clears old AI mutation results after refreshing offers, and identifies whether errors came from search or AI.

**Fallback truth:** Groq/OpenRouter only run when explicitly configured/enabled and when the primary encounters one of the permitted transient failure categories. A visible product card, by itself, does not establish that any LLM ran.

## 3. PayPal Sandbox account conflict

PayPal message: *"You are logging into the account of the seller for this purchase."*

This comes from the PayPal **buyer approval session** being signed in as the same **Business Sandbox seller** that owns the app's client ID/secret. The server legitimately initiates a Sandbox order using the seller's credentials. PayPal prohibits that same account from paying itself.

**Correct steps:**
1. At https://developer.paypal.com/dashboard/accounts locate two distinct Sandbox accounts: **Business** (merchant/seller, API credentials) and **Personal** (buyer, checkout approval).
2. Use the Personal Sandbox account to approve the checkout. If PayPal is already signed in as Business, select **Log Out**, then reopen the existing approval link in a separate private/incognito browser context and sign in as Personal.
3. Never use a real PayPal account or change the backend's merchant API credentials to buyer credentials.
4. After buyer approval returns, confirm the exact amount and currency and perform the application's explicit Sandbox **capture**. Confirm stored order/capture IDs and successful signed webhook reconciliation. Do not create multiple new PayPal orders just to retry the login.

Official PayPal documentation: https://developer.paypal.com/sandbox-testing/accounts and https://developer.paypal.com/api/get-started/ .

The code can explain the proper account role but **cannot choose or provision the user's PayPal Personal Sandbox credentials** without their action.
